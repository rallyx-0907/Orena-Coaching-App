## Findings

1. **P2 — Account deletion does not reach these rows.** The docstrings, the proposal and D-17H said a deleted account's
   rows go with it by `ON DELETE CASCADE`, but the `users` row survives deletion (incarnation barrier and journal anchor,
   `deletion_enumeration.py:3-6`, D-054/D-055), so the cascade never fires, and `ai_cost_records` was not in the deletion
   enumeration, while `account-deletion.*.json:41` promises that records of AI use and cost are deleted. A re-registered
   account (same `users.id`) would also inherit the deleted incarnation's spend in the admin view and later in quota. P2,
   not P1: no deletion runtime exists yet (D-055), and `usage_events` and feedback follow the same existing pattern.
2. **P2 — One write error stops recording for every account in that process for 5 minutes** (`account_costs.py:66-71`).
   Acceptable for an Admin report; a silent undercount if per-plan quota ever reads this table. Revisit before any quota
   reads `ai_cost_records`. Not blocking.
3. **P3 — The migration docstring and D-17H cited this review file before it existed.** Any wording fix to the
   migration changes `chain_digest`/`execution_digest`, so it must land before the rehearsal.
4. **P3 — `migrations/proposed/README.md` stated the review and rehearsal as done.**
5. **P3 — `D-17H` is a placeholder; D-17H cited `D-173`, absent from the log at this commit** (it is on PR #128).
6. **P3 — Comments still called 0026 "proposed"** (`models.py:634`, `platform_repository.py:879`, `account_costs.py:11`).
7. **P3 — The published "13 months" is literal** while `ai_costs.retention_days` (90..396) can shorten it. Make it a fact or
   record that the published value is the default. Not blocking.
8. **P3 — ORM `provider`/`model` use Python `default=""`** against `server_default=""` in the migration. Cosmetic.
9. **P3 — `scripts/rehearse_grammar_content_store.py:554, 959-963` hard-codes 0030 as head**: a one-off rehearsal record,
   not in CI; its head checks fail if re-run. Note only.

### Confirmed correct

- **DDL**: types match the proposal; FK `users.id ON DELETE CASCADE`, NOT NULL; the `cost_state` CHECK matches the
  sanitizer's four states and the writer's `'unknown'` fallback; `cost_usd >= 0` and the unit ranges fit the columns;
  two indexes; `downgrade` drops both, then the table.
- **ORM model** matches the migration column for column, CHECK for CHECK, index for index (finding 8 aside).
- **Lock impact on :8000**: `CREATE TABLE ... REFERENCES users` takes `SHARE ROW EXCLUSIVE` on `users` (blocks writes,
  not reads), on an empty new table, in one transaction with the version update — milliseconds; with web and worker
  stopped as the pack requires, no contention.
- **Chain integrity**: 0026 parents on 0030; proposed 0027 still parents on 0026, 0028 on 0027. Nothing orders
  migrations by file name: startup uses `get_current_head()`, the pack `iterate_revisions` (its sort only feeds a
  digest), the corpus rehearsal now reads the head from Alembic; no test or script asserts 0030 is head.
- **Request path**: one `INSERT ... SELECT` with 500 ms statement and 200 ms lock timeouts; exceptions caught twice;
  anonymous, local and operator calls excluded; the archive repository is a no-op. The pool-checkout wait is not covered
  by the timeouts (minor).
- **Sweep**: at most once a day per process on a daemon thread, bounded batches, oldest first, only this table, period from
  `ai_costs.retention_days`.
- **Privacy**: no content columns; the per-account view is admin-only and audited on every look, top 100, 90 days.
- **Tests are not weakened**: the head check in `test_ai_account_costs.py` is stronger (exists only in `versions/`,
  single head 0026, parent 0030); the PostgreSQL proof now runs through `env.py`; the grammar migration test's exact-head
  pin is relaxed only because 0030 is no longer head, and the exact head is pinned in the AI cost test; `test_billing.py`
  correctly drops the manual 0026 apply.
- **The pack handles an additive step**: generic gated step; the new empty table is reported in `new_tables`, not a
  failure; `verify_after` requires readiness at the new head.
