## Reading the result

- **Group 3** is the lock proof: another session held every one of the 56 pre-existing tables (all except `alembic_version`)
  in `ACCESS EXCLUSIVE` mode while the upgrade ran with `lock_timeout = 5s`; the upgrade completed, so the revision needs no
  lock on `grammar_progress`, `users` or any existing table.
- **Group 4/5**: the schema outside the eight tables is identical before and after the upgrade; the downgrade restores the
  0029 schema exactly (columns, constraints, indexes, triggers, functions) and a second upgrade reproduces the first.
- **Group 9**: the third row shows both concurrent publishes committing one after the other: `SELECT ... FOR UPDATE` on the
  point row serializes them, the later one supersedes the earlier, exactly one version is published, and the revision moved
  once per committed publish.
- **Group 10**: at 1,000 points the planner sorts the catalogue in memory (0.7 ms) rather than walk
  `ix_grammar_points_catalog`; with sequential scans disabled the index serves the same query, so it is usable when the
  catalogue grows. Every other read path chose its intended index by default.
- **Group 11**: "reversed-order violations observed" is informational; it shows the hazard the proposal's revision-first
  order (or one REPEATABLE READ transaction) prevents. Revision-first reads had zero violations.
