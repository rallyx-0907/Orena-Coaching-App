# Reading on demand: translation, summary, contextual meaning

Human decisions of 2026-10-05. Translation, the summary and the contextual meaning of a word are **generated by the
AI when a learner asks, once, and kept**. Opening an article calls none of them. A provider failure is a retryable
error, never "feature not available". No live provider is called in QA: tests use fakes.

## One cache for all three

`writing_coach/reading_derived.py`. Key = sha256 of the kind, the learning language and the **normalized text**
(NFC, whitespace collapsed; the word's text is also case-folded), plus the support language. Never a segment id, a
route or a screen. Two layers:

- in-process LRU (4096 entries), always on;
- the table `reading_derived_texts`, **only for published text**, and only once the migration below is applied.
  Before that, or on any database error, persistence pauses for five minutes and the learner is served from
  memory (same pattern as `ai/account_costs.py`).

`content_id` (optional string on the requests below) says where the text is from. **Only `article:<uuid>` reaches
the shared table.** Absent, or `book:...`, or anything else: in-process only, because what is derived from a
learner's own imported text is learner-owned (D-104) and no account-bound cache exists yet. Failures and empty
answers are never cached.

## Endpoints

### `POST /api/reading/translate` (contract kept)

Request: `{source_language, target_language, content_id?, segments:[{segment_id, text}]}` (max 48 segments).
Ask **per sentence** (ids like `p3s2`): the Reader paragraph (its sentences joined) and the Sentence Quick Sheet
Translation tab (one segment) then share the same cached unit, so a sentence is generated once.
Response 200: `{status, source_language, target_language, translations:[{segment_id, translated_meaning}]}` with
`status` = `ready` | `not_required` (support language equals the text's) | `too_large`.
**Changed:** an engine failure is no longer 200 `status:"unavailable"`; it is **503**
`{"detail":{"category":"translation_unavailable","retryable":true,...}}`. (`scripts/fixtures/api/reading_translate.json`
still holds the old `unavailable` sample.) Other errors unchanged (409 language mismatch, 422 support language).

Engine: `READING_TRANSLATION_PROVIDER` = `ai` (**default**: the platform capability `learner_translation`, so the
operator's provider/model and the cost record apply), `local` (Marian) or `groq`. Chosen once at start-up; no
runtime failover. `ai` was made the default because the local translator is not part of the standard stack.

### `POST /api/reading/summary`

Request: `{source_language, target_language, article_id | (book_id + chapter_id) | text}` - exactly one text, else
422. Response 200: `{status:"ready", source_language, target_language, bullets:[...]}` (about 5 one-line bullets
in the support language). Errors: 503 `reading_summary_unavailable` `retryable:true` (provider failed or answered
nothing), 404 `reading_article_not_found`, 409 language mismatch, 422 empty/invalid. Only an `article_id` text is
stored in the shared table; a chapter or `text` is process-memory only. Long texts are summarised from their first
12,000 characters. Capability used: `text_discussion` (a new `reading_summary` capability would need a
configuration row in every runtime for no gain).

### `POST /api/dictionary/word-detail` and `/sentence-sheet` (existing; now cached)

New optional request field `content_id`. Cached in front of the gloss (`depth:"sheet"`) and the explanation
(`depth:"full"`, and the sentence sheet). **The learner's own `question` (tutor) path is never cached.**

New response fields on both: `contextStatus` = `ready` | `empty` (answered nothing: no contextual meaning) |
`provider_error` | `skipped` (`contextual:false`), and `retryable` (true only for `provider_error`). So the UI can
tell "no contextual meaning" from "the provider failed - offer retry". With `provider_error` the word sheet still
answers from the dictionary (`meaningSource:"dictionary"`, `available:true`) when it has one.

"Why here?": the contract's `deeper.whyHere` (WordDetail.json). The sheet-depth gloss now also asks for one short
sentence (`why_here`, same single call) and fills `deeper.whyHere` when the full explanation's
`judgement_reason`/`usage_note` is absent. `contextMeaning` (the meaning in this sentence) stays primary;
the dictionary meaning is only the fallback, as before. No new endpoint `/api/reading/gloss` exists.

`POST /api/reading/lookup` keeps its contract. With the `ai` engine it no longer falls back to machine translation
(its docstring: never AI); the contextual meaning is `/word-detail`'s.

## What the UI shows

- Loading: while the call is in flight (first time a sentence/summary/word is asked; later it is instant).
- Error: any 503 with `retryable:true`, or `contextStatus:"provider_error"`: a "try again" control on the same
  surface; never the "not available" state.
- `too_large`: the single sentence is over the batch limit (6,000 characters).

## Migration proposal

`migrations/proposed/20261005_0028_reading_derived_texts.py` (parent 20261005_0027; Alembic does not read it).
Table `reading_derived_texts`: PK (`kind`, `content_hash`, `target_language`), `source_language`, `payload` JSON,
`provider`, `model`, `created_at`; kinds `translation|summary|gloss|explanation`. No account column, first writer
wins, no retention sweep (public-content derivatives; `created_at` indexed). Model:
`ReadingDerivedText`; repository: `persistence/reading_derived_repository.py`. **Gate:** independent review, the
rehearsal, the human's authorization (D-002: startup never applies it). `tests/test_reading_on_demand.py` proves
upgrade, first-writer-wins, constraints and downgrade on PostgreSQL when `ORENA_TEST_POSTGRES_URL` is set. Until it
is applied, everything works from process memory (lost on restart, so a restart regenerates).

## Rate limits

`reading_ai` group: `/api/reading/translate` and `/api/reading/summary`, 300 requests per 10 minutes per account.
Word detail and sentence sheet stay in `dictionary_ai`.
